# YouTube rate limits: what blocks ctxr, what works, what it costs

Written 2026-09-21 against primary sources only (project READMEs and wikis, installed source code, provider pricing pages, YouTube's own terms and API docs). Every claim carries the link it came from. Versions checked: yt-dlp 2026.08.19 and youtube-transcript-api 1.2.4, both as locked in `uv.lock` and installed in `.venv` (the README assumed 1.2.2; the lock file says 1.2.4).

## Recommendation

What ctxr does today, from `src/ctxr/cli.py`: `download()` runs yt-dlp with `-t sleep`, retries a failed download after 15, 45 and 90 seconds while switching the player client to `ios`, then `android`, then back to the default; `get_transcript()` calls youtube-transcript-api twice with a 5 second pause, then falls back to local faster-whisper. That got 35 videos through with zero failures at about one video per minute after the first blocks.

### For about 100 videos (a one-off batch from a home connection)

1. Keep the pacing and spend nothing. yt-dlp's own wiki puts the guest-session limit at roughly 300 videos per hour and recommends a 5 to 10 second delay via `-t sleep` ([yt-dlp Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#common-youtube-errors)). One video per minute is far under that. 100 videos is under two hours.
2. Stop making the extra caption requests. Every youtube-transcript-api call is three requests (watch page, `youtubei/v1/player` with an Android client context, then the caption file), and ctxr repeats it once on failure, so a blocked IP gets six more hits per video. Verified today: yt-dlp's default client lists the English auto-captions in json3 and srt without a PO token (see the verification log). Fetch them in the same yt-dlp call (`--write-auto-subs --sub-langs "en.*" --sub-format json3`) and keep Whisper as the fallback. Also add a circuit breaker: after the first `IpBlocked` or `RequestBlocked`, skip YouTube captions for the rest of the run instead of retrying per video.
3. Fix the retry ladder. The `ios` and `android` clients need a PO token for their media URLs ([yt-dlp PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide#current-po-token-enforcement); `GVS_PO_TOKEN_POLICY ... required=True` in the installed `yt_dlp/extractor/youtube/_base.py`), and today `ios` returned zero downloadable formats for this session (verification log). Those two attempts are pure sleeps. Retry with the default client after the same waits instead.
4. If media URLs still return 403 every few videos, wait an hour and resume; the folder-level `manifest.json` skip already makes resumption free. The caption block observed this morning had lifted by 03:50 UTC.

### For about 1,000 videos

1. Make the same three code changes. At one video per minute that is about 17 hours of wall time; run it overnight, or over two or three nights. Cost: zero.
2. Prefer `--whisper-all`. It removes the caption endpoint (the first thing YouTube blocked) from the loop entirely. The only cost is local CPU time, which this write-up did not measure (open question).
3. If the transcripts must be YouTube's own captions, buy a small rotating residential proxy package and route only the caption requests through it: `YouTubeTranscriptApi(proxy_config=WebshareProxyConfig(...))` with the default `retries_when_blocked=10`, or `GenericProxyConfig(https_url=...)` for any other provider's rotating gateway. Entry prices are $3.50 to $8 per GB (table below). Caption traffic per video is a watch page plus one JSON plus one caption file, so a 1 GB plan goes a long way; measure before buying (open question). Do not route the 720p video through a residential proxy unless you accept paying per gigabyte for tens of gigabytes: this morning's test video alone was 5.46 MiB of 720p60 video plus 2.32 MiB of audio.
4. Keep a PO token provider (bgutil) plus the `mweb` client as the fix for the day the default client stops working, not as a rate-limit fix. yt-dlp's wiki recommends it "if you are having issues with the default clients" ([Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#youtube)), and the plugin's own README says a PO token "does not guarantee bypassing 403 errors or bot checks" ([bgutil README](https://github.com/Brainicism/bgutil-ytdlp-pot-provider#bgutils-pot-provider)). ctxr's default client (`visionos`) does not need one today.
5. Do not use cookies, Tor, cloud VMs or datacenter proxies. Reasons and sources are in the evidence sections.

Every option here is automated access to YouTube without written permission, which YouTube's terms prohibit. Pacing lowers the chance of a block; it does not change the terms position. Proxies and PO tokens go further, into the clause about circumventing features that limit use of the Service. See the Terms section.

## Evidence by topic

### 1. youtube-transcript-api (1.2.4 installed)

How a fetch works, from the installed source (`.venv/lib/python3.11/site-packages/youtube_transcript_api/_transcripts.py` and `_settings.py`):

1. `GET https://www.youtube.com/watch?v={video_id}` and pull `INNERTUBE_API_KEY` out of the HTML (a second GET happens if a consent page comes back).
2. `POST https://www.youtube.com/youtubei/v1/player?key={api_key}` with `{"client": {"clientName": "ANDROID", "clientVersion": "20.10.38"}}`.
3. Read `captions.playerCaptionsTracklistRenderer.captionTracks[].baseUrl` and `GET` that URL for the chosen language.

What each error means, from `_transcripts.py` and `_errors.py`:

- `IpBlocked` is raised when any response is HTTP 429, or when the watch page has no API key and contains `class="g-recaptcha"`.
- `RequestBlocked` is raised when the player response says `playabilityStatus.status == "LOGIN_REQUIRED"` with reason "Sign in to confirm you're not a bot". `IpBlocked` is a subclass of `RequestBlocked`.
- `PoTokenRequired` is raised when the caption URL contains `&exp=xpe`. The error text asks you to open a GitHub issue; the library has no PO token support.
- The library's own error text lists the two causes it knows: "You have done too many requests and your IP has been blocked by YouTube" and "You are doing requests from an IP belonging to a cloud provider (like AWS, Google Cloud Platform, Azure, etc.). Unfortunately, most IPs from cloud providers are blocked by YouTube." (`_errors.py`, `RequestBlocked.BASE_CAUSE_MESSAGE`).

README guidance ([Working around IP bans](https://github.com/jdepoix/youtube-transcript-api?tab=readme-ov-file#working-around-ip-bans-requestblocked-or-ipblocked-exception)): "Same can happen to the IP of your self-hosted solution, if you are doing too many requests. You can work around these IP bans using proxies. However, since YouTube will ban static proxies after extended use, going for rotating residential proxies provide is the most reliable option." The author tested providers and integrated Webshare (with referral links; purchases through them fund the project).

Proxy classes, from `proxies.py`:

- `GenericProxyConfig(http_url=None, https_url=None)`: at least one is required; whichever is given is used for both schemes. The docstring says any HTTP, HTTPS or SOCKS proxy that the requests library accepts.
- `WebshareProxyConfig(proxy_username, proxy_password, filter_ip_locations=None, retries_when_blocked=10, domain_name="p.webshare.io", proxy_port=80)`. It builds `http://{username}[-CC...]-rotate:{password}@p.webshare.io:80/`, so every request goes through Webshare's rotating gateway. `filter_ip_locations=["de", "us"]` restricts the pool to those countries. It also sets `Connection: close` so a rotated IP is actually used per request (`prevent_keeping_connections_alive`).
- `retries_when_blocked`: `_fetch_captions_json` retries the whole three-step fetch that many times on `RequestBlocked`; without a proxy config it is 0. `_api.py` additionally mounts a urllib3 `Retry(total=retries_when_blocked, status_forcelist=[429])`.
- The docstrings and error text insist on Webshare's "Residential" package, "NOT 'Proxy Server' or 'Static Residential'", and add: "The free tier also uses 'Proxy Server' and will NOT work!" (`_errors.py`, `WITH_WEBSHARE_PROXY_CAUSE_MESSAGE`).
- CLI equivalents: `--webshare-proxy-username`, `--webshare-proxy-password`, `--http-proxy`, `--https-proxy` ([README, CLI section](https://github.com/jdepoix/youtube-transcript-api?tab=readme-ov-file#working-around-ip-bans-using-the-cli)).

Cookies are not supported right now. `_api.py` carries the comment "Cookie auth has been temporarily disabled, as it is not working properly with YouTube's most recent changes", the README says "this feature is currently not available" ([Cookie Authentication](https://github.com/jdepoix/youtube-transcript-api?tab=readme-ov-file#cookie-authentication)), and the `RequestBlocked` error text calls cookies "NOT RECOMMENDED" because "YouTube will eventually permanently ban the account".

The README's own warning: "This code uses an undocumented part of the YouTube API, which is called by the YouTube web-client. So there is no guarantee that it won't stop working tomorrow" ([Warning](https://github.com/jdepoix/youtube-transcript-api?tab=readme-ov-file#warning)).

### 2. yt-dlp (2026.08.19 installed)

Rate limit statement (the only numbers any maintainer publishes): "With the default yt-dlp settings, the rate limit for guest sessions is ~300 videos/hour (~1000 webpage/player requests per hour). For accounts, it is ~2000 videos/hour (~4000 webpage/player requests per hour)." The error that signals it is "This content isn't available, try again later", and the advice is "a delay of around 5-10 seconds between downloads with `-t sleep`" ([Extractors wiki, Common YouTube Errors](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#common-youtube-errors)).

Sleep options, from `yt-dlp --help` (2026.08.19): `-t sleep` expands to `--sleep-subtitles 5 --sleep-requests 0.75 --sleep-interval 10 --max-sleep-interval 20`. `--sleep-requests` is "Number of seconds to sleep between requests during data extraction"; `--sleep-interval` / `--max-sleep-interval` bound a random pause before each download; `--sleep-subtitles` pauses before each subtitle download. The README promises preset names will not be removed ([README, Preset Aliases](https://github.com/yt-dlp/yt-dlp/blob/2026.08.19/README.md#preset-aliases)).

Retries: `-R, --retries` (default 10) for HTTP errors, `--extractor-retries` (default 3) for "known extractor errors", `--retry-sleep [TYPE:]EXPR` to space them, e.g. `--retry-sleep extractor:exp=1:20` (`yt-dlp --help`, Download and Extractor Options).

Proxy: `--proxy URL` takes HTTP, HTTPS or SOCKS, e.g. `socks5://user:pass@127.0.0.1:1080/` (`yt-dlp --help`, Network Options).

Clients and PO tokens. The default client list is `visionos,web`; "If no JavaScript runtime/engine is available, then `web` is omitted"; with logged-in cookies it becomes `web_embedded,tv_downgraded,web` ([README, youtube extractor arguments](https://github.com/yt-dlp/yt-dlp/blob/2026.08.19/README.md#youtube)). This Mac has no deno, and yt-dlp only enables deno by default (`--js-runtimes` help text), so ctxr runs on `visionos` alone; the verification log confirms it. The wiki's enforcement table says which clients need a token: `web` for subtitles and media ("Only SABR formats available"), `mweb` for media, `ios` and `android` for media unless a player token is present, `visionos` is not listed at all, `tv` and `web_embedded` and `android_vr` "Not required" ([PO Token Guide, enforcement table](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide#current-po-token-enforcement)). The installed `_base.py` matches: `visionos` carries no `GVS_PO_TOKEN_POLICY` (so the default `required=False`), while `web`, `web_safari`, `mweb`, `ios`, `android` and `tv_simply` set `required=True` for HTTPS formats. yt-dlp itself cannot generate tokens: "Due to the nature of these tokens, yt-dlp cannot generate them and they must be provided externally" ([Extractors wiki, YouTube notice](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#youtube)).

What the maintainers say causes 403 on media URLs:

- Missing PO token on a gated client: "Without it, requests for the affected clients' format URLs may return HTTP Error 403, or result in your account or IP address being blocked" ([PO Token Guide, Introduction](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide#introduction)). yt-dlp hides those formats by default with the message "formats require a GVS PO Token which was not provided. They will be skipped as they may yield HTTP Error 403" (`_video.py`, `_report_pot_format_skipped`); `--extractor-args "youtube:formats=missing_pot"` shows them anyway ([README, formats](https://github.com/yt-dlp/yt-dlp/blob/2026.08.19/README.md#youtube)). Since ctxr uses `visionos`, this is not the cause of ctxr's 403s.
- SABR: "SABR is a custom streaming protocol built by YouTube"; on affected clients "YouTube has removed the playback links for `adaptiveFormats` in the player response", which yt-dlp reports as "Some ... client https formats have been skipped as they are missing a URL" ([issue #12482 by coletdjnz](https://github.com/yt-dlp/yt-dlp/issues/12482), `_video.py`). That is exactly what `ios` produced today. The known-issues page's answer is "Try using PO Tokens with the `mweb` or `web_creator` player clients" ([pinned issue #3766](https://github.com/yt-dlp/yt-dlp/issues/3766)).
- IP blocked while logged out: for "Sign in to confirm you're not a bot" the pinned issue says "Your IP has been blocked by YouTube while you are logged out. You can pass logged-in cookies; however, doing so may get your account blocked. The safer solution is to use a different IP." and for the account variant "Avoid passing cookies, or add a sleep delay to each download" ([pinned issue #3766](https://github.com/yt-dlp/yt-dlp/issues/3766)). The extractor's own message when every client fails is "All player responses are invalid. Your IP is likely being blocked by Youtube" (`_video.py`).
- Immediate 403 on download is a separate row in the known-issues table (#11868) whose listed workarounds, as summarised from that table, are `--force-ipv4`, a different IP, and cookie changes ([pinned issue #3766](https://github.com/yt-dlp/yt-dlp/issues/3766)). `-4` is free to try.
- HTTP 429 in general: "the service is blocking your IP address because of overuse. Usually this is a soft block" ([FAQ wiki](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#http-error-429-too-many-requests-or-402-payment-required)).

Cookies. `--cookies-from-browser BROWSER[+KEYRING][:PROFILE][::CONTAINER]` supports brave, chrome, chromium, edge, firefox, opera, safari, vivaldi and whale, and `--cookies FILE` takes a Netscape file (`yt-dlp --help`; [FAQ, How do I pass cookies](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#how-do-i-pass-cookies-to-yt-dlp)). For YouTube the wiki adds a caution: "By using your account with yt-dlp, you run the risk of it being banned (temporarily or permanently). Be mindful with the request rate and amount of downloads you make with an account. Use it only when necessary, or consider using a throwaway account." It also says not to use `--cookies-from-browser` for YouTube because the browser rotates the cookies; export from a private window that you then close ([Extractors wiki, Exporting YouTube cookies](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#exporting-youtube-cookies)). OAuth login "no longer works with yt-dlp" (same page).

Subtitles path. yt-dlp reads `captions.playerCaptionsTracklistRenderer.captionTracks[].baseUrl` from the player response of whichever client it used, then builds one URL per format by adding `fmt=json3|srv1|srv2|srv3|ttml|srt|vtt`, and, when it has a subtitles PO token, `pot`, `potc` and `c` (`_video.py`, `process_language` and the captions loop). A track "requires a PO token" if its URL's `exp` parameter contains `xpe` or `xpv`, or the client's `SUBS_PO_TOKEN_POLICY` says so; `visionos` has no such policy. So yt-dlp and youtube-transcript-api hit the same three hosts (watch page, `youtubei/v1/player`, the caption URL); the differences are the client used for the player call (`visionos` vs an Android context) and the extra query parameters. Nothing in either source shows one endpoint surviving a block that hits the other; both worked from this IP within four minutes today.

JS runtime. "To download from YouTube, yt-dlp needs to solve JavaScript challenges presented by YouTube using an external JavaScript runtime"; deno is recommended and the only one enabled by default ([EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)). Without one, yt-dlp warns that "YouTube extraction without a JS runtime has been deprecated, and some formats may be missing" (`_video.py`). Today's `mweb` run failed n-challenge solving for this reason.

### 3. PO token provider (bgutil-ytdlp-pot-provider)

Tokens are produced by "an attestation provider on Web, Android and iOS platforms to attest the requests are coming from a genuine client"; "Most PO Tokens (such as for `web` GVS/Player) are bound to the video ID, so a new token is required for each video"; lifespan "possibly as short as 12 hours" ([PO Token Guide, Technical details](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide#technical-details)). Manual extraction is "no longer recommended"; the wiki's TL;DR is a provider plugin feeding the `mweb` client ([PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)).

bgutil generates tokens locally with a BotGuard interfacing library. Setup: yt-dlp 2025.05.22 or newer; Node 22+ or Deno 2+ (or Docker); an HTTP server on `127.0.0.1:4416` (`node build/main.js` after `npm ci && npx tsc`); then `pip install -U bgutil-ytdlp-pot-provider` into the same environment as yt-dlp; check with `yt-dlp -v`, which should list `bgutil:http` under PO Token Providers ([bgutil README](https://github.com/Brainicism/bgutil-ytdlp-pot-provider#installation)). yt-dlp finds pip-installed plugins through the `yt_dlp_plugins` namespace ([README, Installing Plugins](https://github.com/yt-dlp/yt-dlp/blob/2026.08.19/README.md#installing-plugins)).

Does it remove the 403s without proxies? The plugin's first line: "Providing a PO token does not guarantee bypassing 403 errors or bot checks, but it may help your traffic seem more legitimate" ([bgutil README](https://github.com/Brainicism/bgutil-ytdlp-pot-provider#bgutils-pot-provider)). It unblocks the token-gated clients (`mweb`, `web`, `ios`, `android`) and the token-gated subtitles; it is not described anywhere as lifting an IP block. For ctxr it matters only if the default client stops working.

### 4. YouTube Data API v3 is not an option for other people's captions

`captions.download` "requires the user to have permission to edit the video", costs 200 quota units per call, needs the `youtube.force-ssl` or `youtubepartner` scope, and returns `forbidden (403)` when "The permissions associated with the request are not sufficient to download the caption track" ([captions.download](https://developers.google.com/youtube/v3/docs/captions/download)). `captions.list` costs 50 units ([captions.list](https://developers.google.com/youtube/v3/docs/captions/list)). The default allocation is "10,000 units per day combined for all other endpoints" plus per-call caps on `search.list` and `videos.insert` ([Getting started, Quota usage](https://developers.google.com/youtube/v3/getting-started#quota)). So the official route only serves channels you can edit, and even then 50 downloads a day exhaust the default quota.

### 6. Zero-cost IP rotation

Tor. yt-dlp accepts it as `--proxy socks5://127.0.0.1:9050` (`yt-dlp --help`, Network Options); tor listens for SOCKS on 9050 by default and Tor Browser on 9150 ([tor manual, SocksPort](https://2019.www.torproject.org/docs/tor-manual.html.en), [Tor FAQ](https://2019.www.torproject.org/docs/faq.html.en)); a fresh circuit is requested with the `NEWNYM` signal on the control port, which "Tor MAY rate-limit" ([control spec, SIGNAL](https://spec.torproject.org/control-spec/commands.html)). The catch is stated by the Tor Project itself: "The Tor network is public, and websites can always detect when connections are coming from Tor" and "Sometimes websites block Tor users because they can't tell the difference between the average Tor user and automated traffic" ([support: website blocking Tor exits](https://support.torproject.org/tor-browser/general/website-blocking-tor-exits/)). Every exit address is published in a machine-readable list ([check.torproject.org/exit-addresses](https://check.torproject.org/exit-addresses), [TorDNSEL](https://metrics.torproject.org/collector.html)), which the Tor Project offers to operators who want to block Tor ([abuse FAQ](https://support.torproject.org/abuse/i-want-to-ban-tor/)). No YouTube or yt-dlp primary source states YouTube's Tor policy; treat it as unverified and likely to hit the same "static IP after extended use" ban the transcript library warns about.

Phone hotspot / carrier-grade NAT. No primary source was found that says YouTube treats mobile carrier IPs differently from home broadband. Checked: youtube-transcript-api README, the yt-dlp FAQ, Extractors and PO Token Guide wikis, the YouTube Data API docs, and YouTube Help's video error page; none mention mobile or carrier IPs. The closest official text is Google Search's "Unusual traffic" page, which only notes that others sharing your internet provider or VPN can trigger the message ([Google Search help](https://support.google.com/websearch/answer/86640)). A hotspot is a different IP, which the yt-dlp maintainers do call "the safer solution" for a blocked logged-out IP ([pinned issue #3766](https://github.com/yt-dlp/yt-dlp/issues/3766)); whether it lasts longer is unknown.

Cloud VMs are worse, not better: "YouTube has started blocking most IPs that are known to belong to cloud providers (like AWS, Google Cloud Platform, Azure, etc.), which means you will most likely run into `RequestBlocked` or `IpBlocked` exceptions when deploying your code to any cloud solutions" ([youtube-transcript-api README](https://github.com/jdepoix/youtube-transcript-api?tab=readme-ov-file#working-around-ip-bans-requestblocked-or-ipblocked-exception)). Invidious's docs say the same from their side: "It is known that YouTube block datacenter and VPN IP addresses" ([Invidious, YouTube errors explained](https://docs.invidious.io/youtube-errors-explained/)).

IPv6 is a related zero-cost lever the Invidious project documents ("Rotate your IPv6 address for escaping YouTube blocking", [ipv6-rotator](https://docs.invidious.io/ipv6-rotator/)); it needs an ISP-routed IPv6 prefix, which was not checked for this connection.

### 7. Alternative endpoints

Invidious exposes `GET /api/v1/captions/:id` with `label`, `lang`, `tlang` and `region`; without a label it returns the caption list, with one it returns WebVTT ([Invidious API](https://docs.invidious.io/api/)). But the project's own instance rules say "Public instances MUST use a system that rotates the IP addresses used for communication with YouTube's servers" and "please host Invidious at home instead of using a public instance", because of "recent YouTube issues" ([instances](https://docs.invidious.io/instances/)); the maintainer note on that issue is "It appears that it affects all the software using YouTube" ([iv-org/invidious#4734](https://github.com/iv-org/invidious/issues/4734)). Playback now requires the Invidious companion, which exists to create PO tokens ([installation](https://docs.invidious.io/installation/), [errors explained](https://docs.invidious.io/youtube-errors-explained/)). Using a public instance moves the same block onto someone else's IP and adds their rate limits.

Piped's `/streams/:videoId` returns a `subtitles` array with `url`, `mimeType`, `code`, `name` and `autoGenerated` ([Piped API](https://docs.piped.video/docs/api-documentation/)). Its self-hosting guide says "Because YouTube tends to ban IP addresses, it is recommended to either use the IPv6 rotator made by the Invidious team or use a VPN or proxy between the Piped backend/proxy and YouTube" ([self-hosting](https://docs.piped.video/docs/self-hosting/)). Same conclusion.

yt-dlp `--write-auto-subs` is the one alternative worth adopting, for the reasons in section 2: it reuses the player response yt-dlp already fetched, so it adds one request per video instead of three, and it does not need a PO token on the default client (verified today). It does not use a different endpoint family, so it is not immune to the IP block; it just stops adding to it.

### 8. YouTube Terms of Service

From the "Permissions and Restrictions" section of [youtube.com/t/terms](https://www.youtube.com/t/terms) (effective January 5, 2022 as shown on the page). "The following restrictions apply to your use of the Service. You are not allowed to:"

> access the Service using any automated means (such as robots, botnets or scrapers) except (a) in the case of public search engines, in accordance with YouTube's robots.txt file; or (b) with YouTube's prior written permission

> circumvent, disable, fraudulently engage with, or otherwise interfere with any part of the Service (or attempt to do any of these things), including security-related features or features that (a) prevent or restrict the copying or other use of Content or (b) limit the use of the Service or Content

> access, reproduce, download, distribute, transmit, broadcast, display, sell, license, alter, modify or otherwise use any part of the Service or any Content except: (a) as expressly authorized by the Service; or (b) with prior written permission from YouTube and, if applicable, the respective rights holders

Plainly: ctxr's downloads and caption fetches are automated access and downloading without written permission (first and third clauses). Rate limits and bot checks are "features that ... limit the use of the Service", so proxies, IP rotation and locally generated attestation tokens sit inside the second clause as well. The consequences YouTube's own tools apply are IP blocks and, with cookies, account bans (sections 1 and 2). This document does not assess legal exposure beyond quoting the terms.

## Open questions

1. Bytes per video on the caption path (watch page plus player JSON plus caption file). Needed to size a proxy plan. Measure with one `curl -s -o /dev/null -w '%{size_download}' https://www.youtube.com/watch?v=<id>` plus the two follow-up requests before buying anything.
2. Which signal produced this morning's `IpBlocked`: HTTP 429 or a reCAPTCHA page. The library maps both to the same class; ctxr only logs the class name. Log `YouTubeRequestFailed.reason` and the status code.
3. Whether the media 403s were all on the `visionos` client. The retry ladder reports only the last stderr line; log the client per attempt.
4. Whether `--write-auto-subs` in a bulk run trips the same block as youtube-transcript-api, or later. Only the listing was verified today.
5. Whisper small throughput on this Mac (seconds of audio per second of CPU), to budget `--whisper-all` for 1,000 videos.
6. Block duration. Observed: at least the rest of the hour this morning; lifted by 03:50 UTC. No primary source documents a duration for guest IP blocks; Invidious's docs mention 24 hours for 429, which is their experience, not YouTube's statement ([errors explained](https://docs.invidious.io/youtube-errors-explained/)).
7. Whether installing deno (which adds `web` back into the default client list) changes anything for ctxr. `web` needs a PO token for media and subtitles, so the likely answer is no, but it also removes the "extraction without a JS runtime has been deprecated" warning.
8. Whether the home ISP hands out a routed IPv6 prefix, which would make the Invidious IPv6 rotation approach possible at no cost.
9. Whether `--force-ipv4` (`-4`) changes the 403 rate; it is listed as a workaround in the known-issues table and costs nothing to try.
